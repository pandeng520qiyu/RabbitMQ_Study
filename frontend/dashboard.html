📚 RabbitMQ 核心概念
📨
Message（消息）
消息是 RabbitMQ 传输的基本单元，由 消息体（Payload） 和 消息属性（Properties） 组成。 消息体是任意字节，属性包含路由键、优先级、TTL、持久化标志等。
基础
🔌
Producer（生产者）
消息的发送方，负责将消息发布到交换机。本项目中 order-service 是生产者，创建/支付/取消订单时发布消息。
基础
🔔
Consumer（消费者）
消息的接收方，订阅队列并处理消息。本项目中 notification-service 是消费者，接收订单事件后发送通知。支持手动 ACK 防止消息丢失。
基础
🔀
Exchange（交换机）
消息路由中枢，接收来自生产者的消息并按类型转发到对应队列。 四种类型：Direct（精确）、Fanout（广播）、 Topic（模糊）、Headers（属性匹配）。
核心
📥
Queue（队列）
消息的存储容器，遵循 FIFO 原则。支持持久化（重启不丢失）、 独占（仅一个连接可用）、自动删除（无消费者时删除）等属性。
核心
🔑
Routing Key（路由键）
生产者发送消息时指定的标签。Direct 交换机要求精确匹配， Topic 交换机支持通配符（* 匹配一个词，# 匹配零或多个词）。
核心
🪢
Binding（绑定）
将交换机与队列关联的规则，绑定时可指定 Binding Key。 交换机根据消息的 Routing Key 与 Binding Key 的匹配规则决定消息去向。
核心
⏰
TTL（消息过期）
为消息或队列设置生存时间（Time-To-Live）。过期的消息会被 丢弃或进入 死信交换机（DLX），可用于延迟队列、订单超时场景。
高级
💀
Dead Letter Queue（死信队列）
消息变为"死信"的三种情况：①消息过期、②队列已满被拒绝、③消费者 Nack 且 requeue=false。 死信会转发到 DLX，是实现延迟消费和容错的重要手段。
高级
✅
消息确认（ACK / NACK）
消费者告知 Broker 消息已处理（ACK）或处理失败（NACK）。 手动 ACK 模式下，消息在确认前不会从队列删除，保证消息不丢失。 本项目所有消费者均使用手动 ACK。
可靠性
📬
Publisher Confirm（发布确认）
生产者通过 Confirm 机制确认消息已到达 Broker（交换机）。 与 Publisher Returns 配合使用，可确保消息从生产者到队列的全链路不丢失。
可靠性
⚖️
Prefetch（预取数量）
消费者每次从 Broker 预取的最大消息数量（QoS 控制）。 设为 1 时，消费者处理完当前消息才获取下一条，实现公平分发， 避免某个消费者堆积过多任务。
性能

4️⃣ 路由匹配（Topic Exchange）

Topic 交换机支持通配符路由，* 匹配一个词，# 匹配零或多个词。 本项目使用 Topic 交换机按订单事件类型路由到不同处理队列。

5️⃣ TTL + 死信队列（延迟消费）

消息发送到 TTL 队列，5 秒后过期进入死信交换机（DLX），再路由到死信队列被消费者处理。 这是实现"订单 N 分钟后自动取消"的经典方案。
